Owner: security-engineer | Gate: G3 | Date: 2026-10-10 | Version: 0.1
Reviewed artifacts (author: principal-architect): `delivery/decisions/adr/ADR-0003-os-level-sandbox.md`, `delivery/G3-solution-design/sandbox-environment.md` (both DRAFT).

Method: STRIDE per trust boundary (browser to API, API to runner, runner to Docker engine, container to runner via stdout, container to kernel/VM). Design-stage review only; no code exists, so every mitigation below is **unverified until the named test passes** (security-policy item 9, rule 5).

## Verdict: CONDITIONAL

The direction (Option A, fresh single-use container behind a narrow runner, engine controls kept as defence in depth, deny-by-default route policy, fail closed) is sound and the container flag set is largely correct. No Critical finding. **Two High findings (SR-01, SR-02) must be resolved in the design documents before either artifact moves to FINAL or G3 is approved.** Medium findings need a design change or a named test before SLICE-001/SLICE-003 start; Low findings may be tracked in the build log.

Conditions for PASS
1. SR-01 and SR-02 fixed in `sandbox-environment.md` (and ADR-0003 where referenced).
2. Medium findings either fixed in the design or recorded with an owner and a test ID in the delivery plan.
3. SR-04 (Windows same-user Docker access) and SR-05 (VM boundary) explicitly accepted in writing by the Founder for a **local-only** demo (security-policy item 9); any hosted or LAN-reachable demo re-opens them as High.
4. S-1..S-9 plus SR-01..SR-20 merged into `threat-model.md` by security-engineer.

## Checks that passed (design level)
- Container flags C3-C13, C18-C21: non-root, read-only root, `noexec,nosuid,nodev` tmpfs with size, `--network none`, `--cap-drop ALL`, `no-new-privileges`, no `--privileged`/`--device`, seccomp not unconfined, pids/memory (swap disabled)/CPU limits, `nofile`/`fsize`/`core` ulimits, `--ipc none`, `--log-driver none`, `--init`, single-use with forced removal and reaper. No `docker.sock` in the container (SBX-FF-1/2). `nproc` ulimit correctly not used (it counts per uid across containers).
- Learner input via stdin only, never argv/env/labels (C16, S-7).
- Hidden checks, expected outputs, probe and mutation answers stay outside the container; container gets only the learner's own seeded tables; seed key never enters it (C15, C18; consistent with T-01b, T-03b, T-09b).
- Fail closed with no automatic fallback in `container` mode (S-9).
- Deny-by-default route table with startup failure on undeclared routes (TAB-FF-1); uniform 404 consistent with invariant 15; reviewer never re-executes learner code (V-CASE); auditor sees hashes only (ux-flows 7.5, invariant 2); alias-only outside learner tabs (G-9, invariant 3).
- No countdown or duration shown to learners (G-8).

## Re-review 1 (2026-10-10, against ADR-0003 v0.2 and sandbox-environment.md v0.2)

I re-checked the revised text directly and did not rely on the author's revision notes. Evidence is cited as section/line in sandbox-environment.md (SE) and ADR-0003 (ADR).

### SR-01: Closed (design level)
Evidence
- SE s3.0 lines 87-104: the `POST /runs` body is a closed schema (`additionalProperties: false`, all required) of `run_id` (canonical UUID v4), `task_id` and `dataset_id` (UUID), `limits_profile` (closed enum) and `submission` (1-10,240 bytes UTF-8). It has no path, image, mount, env or option field.
- SE line 104: the runner builds the argv from a fixed template and fills in only (a) the re-validated `run_id` label, (b) the mount source from the manifest entry, and (c) enum constants. SE C15/C16 (lines 73-74) and ADR line 43 are consistent with this.
- SE lines 106-109 and step 2 (line 114): the API builds no files. The store is populated offline, read-only at run time and hash-verified per run (line 101). The manifest has no path field (line 107), so the mount source is derived from `dataset_id`.
- I traced every request field to every Docker sink. `run_id` reaches a label only after canonical-UUID validation. `task_id` and `dataset_id` reach the mount source only via manifest lookup. `limits_profile` maps to constants. `submission` reaches stdin only. The image comes from the pinned digest in config. No remaining path from API input reaches a mount, image name, env var, argv value or label.
- SBX-FF-7..10 (ADR lines 127-130) would catch traversal in any field, unknown IDs, unknown/case/empty/numeric enum values, oversize and invalid-UTF-8 input, extra fields (`image`, `mounts`, `privileged`, `env`, `cmd` and similar) and any argv drift (golden test).

Residual gaps (do not reopen SR-01; tracked as SR-21 Low):
- The UUID regex must be ASCII-only (`[0-9a-f]` with `re.ASCII`, or `uuid.UUID(...)` round-tripped to the canonical string). Python `\d` matches non-ASCII digits.
- The runner should build the mount source as `<store>/<dataset_id>.sqlite`, then `realpath` it and check containment, so a symlink planted in the store cannot redirect the mount.
- Missing tests: a valid `task_id` and `dataset_id` that do not belong together; any `py_*` profile is rejected while Q1 is open; manifest hash mismatch after a file is swapped; an HTTP body larger than the cap is rejected before JSON parsing (SR-08 is still open).
- A compromised API can still pick **any** published `dataset_id`, including another learner's pool entry. The runner holds no identity, so this is by design. The API-side mapping (session to `dataset_id`) is therefore the control and needs its own test (SR-23).

### SR-02: Closed for the role model; two related items Partly addressed
Evidence
- SE s4.1 R-1 (line 155): the role comes only from the server-side session record. The session ID is opaque and `HttpOnly`, and the role is never read from cookie body, header, query, body or local storage.
- R-2 (line 156): sign-up is learner-only and the schema rejects unknown fields. R-3 (line 157): staff roles are assigned out of band and never offered in UI. R-4 (line 158): track is a closed-enum preference, grants no privilege and is not accepted on staff accounts. R-5 (line 159): the demo switcher route is not registered unless `DEMO_MODE=on`. R-6 (line 160): changes are hash-chain audited. R-7 (line 161): role change invalidates sessions.
- TAB-FF-6..10 (ADR lines 131-135) cover sign-up role injection, tampered or forged role claims, track-change privilege, demo switcher absence and audit completeness.

Partly addressed (new IDs below):
- The demo switcher is the realistic bypass during the actual demo (SR-24).
- Cookie sharing across localhost ports (SR-13) is not addressed. R-1 does not distinguish HR sessions from shell sessions, so SR-13 stays Open (Medium).
- A general account or profile update route is not excluded explicitly. TAB-FF-6 tests sign-up only (SR-26).
- If an external identity provider is used, R-1 trusts "the identity provider's verified claim". That attribute must be admin-controlled, not user-editable (SR-26).

### Matrix with both learner tracks (SE s4.2, lines 163-190)
- Staff columns deny every learner row. Learner columns deny every staff row. PY rows deny DA, and DA rows deny PY. `X-HELP` is allowed for all. Deny-by-default holds **per tab**.
- **Problem: per route it is not well defined (SR-25).** `POST /me/runs`, `PUT /me/drafts/{task}`, `POST /submissions`, `GET /me/workspace/brief` and `GET /me/runs/{run_id}` each appear under both a PY tab and a DA tab. Line 144 declares one `{tab_id, roles, track}` per route, and line 145 derives `limits_profile` from (track, **tab**, action). The server cannot know the tab for a shared route unless the client sends it, which would make the tab client-influenced.
- Routes missing from the matrix: `PUT /me/track` (R-4) and `GET /shell/tabs`. With TAB-FF-1 these fail startup or are denied. Add them as rows.
- SR-03 (object ownership under `/me/{id}`) is still open. Line 146 is unchanged, and the new `GET /me/runs/{run_id}` route adds one more object route that needs an ownership check.
